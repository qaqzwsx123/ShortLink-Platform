# ShortLink-Platform

一个短链接管理项目，支持用户登录、分组管理、短链接创建与批量创建、访问跳转、回收站和访问统计。项目包含管理服务、短链接服务、网关和聚合服务，可以按微服务方式运行，也提供聚合部署方式。

后端以 Java 17、Spring Boot 3、Spring Cloud 和 Spring Cloud Alibaba 为基础。Nacos 负责服务注册与发现，Sentinel 对短链接创建等接口进行 QPS 限流；Spring Cloud Gateway 负责统一路由和登录态校验，OpenFeign 配合 Spring Cloud LoadBalancer 完成服务间调用。

主要技术栈及用途：

- **数据存储：** MySQL、MyBatis-Plus、ShardingSphere-JDBC，处理业务数据持久化、分页查询、数据分表和敏感字段加密。
- **缓存与并发控制：** Redis 缓存短链接映射和登录状态；使用 Redisson 分布式锁、布隆过滤器、空值缓存和缓存预热，处理重复注册、缓存击穿与缓存穿透等问题。
- **异步统计：** 使用 Redis Stream 传递访问统计事件，消费者完成数据入库并做幂等处理，统计内容包括 PV、UV、UIP、访问地区、浏览器、操作系统和设备类型。
- **流量控制与故障处理：** Sentinel 接口限流、Redis Lua 用户请求限流；Redis 不可用时提供本地限流、受并发限制的数据库查询兜底，并隔离统计发送失败对跳转流程的影响。
- **前端控制台：** Vue 3、Vite、Element Plus、Vue Router、Vuex、Axios 和 ECharts，完成页面构建、组件交互、路由、状态管理、接口请求和统计图表展示。
- **辅助组件：** Jsoup 获取目标网站标题与图标，配合 Hutool、Fastjson2、Lombok 等工具完成常用数据处理。

### 问题排查与处理记录

下面结合已有代码和修复记录，补充几个问题的表现、定位思路和处理方式。日期沿用上面的功能时间轴。

#### 6月23日：热点链接缓存失效后，请求一起查数据库

**问题：** 短链接平时可以从 Redis 直接拿到跳转地址，但热点链接的缓存一旦失效，同一时间进来的请求就可能一起查数据库。单个请求的逻辑看起来没有问题，并发起来却会重复回源。

**分析：** 关键在于“没查到缓存”和“把数据重新放回缓存”之间有一段空档。只在方法开头查一次缓存，后面进来的请求也会认为自己需要查库。无效链接则是另一个问题：数据库本来就没有记录，反复查询也不会有结果。

**处理：** 常规回源流程按完整短链接加分布式锁，拿到锁后再查一次缓存，已有结果就直接使用。创建链接时预热缓存；对不存在的链接先用布隆过滤器拦截，查询后确认无效的结果再写入空值缓存，减少重复空查。

#### 7月13日：永久有效的链接，在缓存没命中时反而报错

**问题：** 永久有效的短链接没有设置过期时间，但跳转逻辑在查询数据库后直接调用了有效期的 `before` 方法，时间为空就会抛出空指针异常。

**分析：** 这个问题容易被缓存遮住：缓存命中时直接跳转，不会走到数据库结果的有效期判断。只看正常命中的路径，很难注意到永久有效和限时有效的字段差别。

**处理：** 先判断链接记录是否存在，再判断有效期是否为空。只有设置了有效期，才继续比较是否过期，永久有效的链接不走日期比较。

#### 7月13日：点击按访问量排序，结果却像是按访客数排的

**问题：** 列表支持按 PV、UV 等字段排序，但原来的 SQL 将累计 PV 和累计 UV 对应的排序列写反了，选择的指标和实际排序不一致。

**分析：** 这类问题不一定是前端表格没有刷新。需要顺着排序参数往下看，确认页面传入的 `orderTag`、Mapper 的条件分支和最终 `ORDER BY` 字段是否对应。

**处理：** 将 `totalPv` 对应到 `total_pv`，`totalUv` 对应到 `total_uv`。这里修正的是排序字段映射，不能靠调整页面上的列名来掩盖后端条件写反的问题。

#### 7月13日：查询多天的浏览器统计，同一种浏览器被拆成多条

**问题：** 浏览器统计按时间范围查询时，原来的 SQL 又把日期放进了分组条件。同一种浏览器在不同日期有访问，就会被拆成多条结果。

**分析：** 日期范围筛选和按天分组是两回事。这里需要的是所选时间段内各浏览器的汇总，不是每天的浏览器明细，`GROUP BY` 中多一个日期字段就改变了统计口径。

**处理：** 保留开始、结束日期作为查询条件，从浏览器汇总的分组字段中去掉日期。单链接查询和分组查询都做对应调整，让结果按需要的浏览器维度聚合。

#### 7月14日：把过期链接重新设为有效，访问还是进失效页

**问题：** 链接过期后，跳转流程会写入空值缓存。后续将链接改成永久有效，或把有效期延长，只更新数据库仍可能继续命中之前的失效标记。

**分析：** 这里不能只检查保存目标地址的缓存，还要检查标记“这个链接无效”的另一份缓存。数据库状态已经恢复，不代表 Redis 里之前留下的失效结论也自动恢复。

**处理：** 有效期发生变化时清理映射缓存；如果原来已经过期，而修改后重新有效，再删除对应的空值缓存。这样下一次访问才有机会重新查询数据库，而不是一直被旧标记挡住。

#### 7月14日：访问明细里的访客类型，总是落到“旧访客”

**问题：** 访客类型查询有结果，但组装访问明细时仍可能取不到类型，最后使用默认的“旧访客”。

**分析：** 原因出在结果字段名：查询返回的键是 `uvType`，代码取值却写成了 `UvType`。Map 的键区分大小写，取不到值又有默认兜底，所以不一定报错，只是展示结果不对。

**处理：** 将单链接明细和分组明细中的取值键统一为 `uvType`，与查询别名保持一致。排查这种“有数据但展示不对”的问题时，也要核对结果映射，不能只盯着查询有没有返回记录。

#### 7月20日：生成短码时，布隆过滤器检查的地址和实际保存的不一致

**问题：** 创建短链接时，域名已经由后端配置控制，但生成短码的查重逻辑还在使用请求参数中的域名，拼出来的完整地址可能与最终保存的地址不同。

**分析：** 布隆过滤器判断的是完整字符串，不是单独的短码。即使短码相同，只要前面的域名不同，检查的就是另一个键；写入和判断必须使用同一套拼接规则。

**处理：** 生成短码时统一使用后端配置的默认域名进行布隆过滤器检查，与实际创建链接的规则对齐。过滤器用于提前筛选，最终并发冲突仍需要数据库唯一约束兜底。

#### 8月2日：两个业务的布隆过滤器用了相同名称

**问题：** 用户注册和短链接创建都需要布隆过滤器，但两边如果使用相同的 Redis 对象名称，就会混用同一个过滤器。

**分析：** 这里容易只看 Spring Bean 的名字，以为方法名不同就是两个对象。实际还要检查 `getBloomFilter` 传入的名称，这个名称才决定 Redis 中使用的是哪一个过滤器。

**处理：** 用户名、短链接和分组标识分别使用独立名称，把不同业务的数据分开。使用时也不能把“可能存在”当成“肯定存在”，最终是否有这条记录仍以数据库为准。

#### 8月5日：已经返回限流提示，后面的业务却还可能继续执行

**问题：** 限流过滤器判断请求超限后，虽然向响应写入了错误信息，但原来没有立即结束方法，代码仍会走到后面的过滤器链。

**分析：** 向响应写数据，不等于 Java 方法自动返回。沿着分支往下看，才能发现“已经拒绝请求”和“继续调用业务”竟然出现在同一次执行中。

**处理：** 在超限分支写完错误响应后立即 `return`，确保不会继续执行 `filterChain.doFilter`。异常分支也要明确结束或进入受控兜底，不能写完响应后继续向下走。

#### 8月5日：注册时没抢到锁，却又在释放锁的地方报错

**问题：** 多个请求注册同一个用户名时，有的请求拿不到分布式锁。原来的结构把抢锁也放在 `try` 里面，失败后仍会进入 `finally` 调用解锁。

**分析：** 没拿到锁的线程不拥有这把锁，解锁时可能再抛出异常，把原本准备返回的注册冲突提示盖掉。需要检查的不是有没有写 `finally`，而是哪些路径会进入它。

**处理：** 先执行 `tryLock`，获取失败就返回业务异常；只有成功拿到锁，才进入包含数据库写入和最终解锁的代码块。数据库唯一键冲突则单独转换成重复注册提示。

#### 8月11日：修改目标地址后，短链接还是跳到原来的页面

**问题：** 修改短链接的原始地址后，数据库里已经是新地址，但访问时仍可能拿到旧的跳转地址。

**分析：** 沿着跳转流程往前看，请求会先读 Redis，命中后根本不会再查数据库。原来的缓存删除条件只比较了有效期类型和有效期，没有把原始地址的变化算进去，所以单独修改地址时旧缓存还在。

**处理：** 将原始地址是否变化也加入缓存失效判断。地址或有效期发生变化时删除对应映射缓存，让后续请求重新查询数据库并回填，避免数据库改了、缓存却一直保留旧值。

#### 8月15日：登录校验通过，不代表可以查询任意分组的统计

**问题：** 统计接口如果只按传入的分组标识查询，就存在修改参数后访问其他用户数据的风险。页面上只展示自己的分组，并不能代替后端权限校验。

**分析：** 要检查的不只是用户有没有登录，还要检查这个分组到底属于谁。单链接统计、分组统计和访问明细都需要检查，不能只补一个入口。

**处理：** 查询统计数据前，先取得当前登录用户名，再根据用户名和分组标识核对归属。未登录或分组不匹配时直接拒绝查询；同时补上访问记录为空时的处理，避免后续转换继续报错。

#### 8月17日：分组标识已经被过滤器命中，代码却仍然把它当成功结果返回

**问题：** 生成分组标识时，如果布隆过滤器判断该标识可能已存在，原来的逻辑会跳过唯一标识表的插入，却仍然返回这个标识。

**分析：** 问题在于“跳过插入”和“允许返回”被混在了一起。一个没有成功登记到唯一标识表中的候选值，不应该直接作为创建分组的成功结果。

**处理：** 过滤器命中时直接返回空结果，让上层重新生成候选值；过滤器未命中才尝试插入唯一标识表，数据库唯一键冲突时同样返回空结果。只有插入成功，才返回这次生成的分组标识。

#### 8月22日：第一次打开统计正常，切换时间范围后却查不到数据

**问题：** 单个短链接的统计弹窗第一次打开时会传链接启用状态，但切换日期后的请求没有继续带上这个参数，两次查询的条件不一致。

**分析：** 只检查开始、结束日期容易漏掉问题。需要将首次查询和切换时间后的参数逐项对比，除了完整短链接和分组标识，还要检查 `enableStatus` 有没有保留下来。

**处理：** 在弹窗保存当前链接信息时一并记录 `enableStatus`，切换时间后查询统计和访问明细都继续传入该字段，避免刷新日期时丢失原来的查询上下文。

#### 8月28日：Redis 限流不可用时，正常请求也会被挡住

**问题：** 用户请求限流依赖 Redis Lua 脚本。Redis 出现异常时，如果直接返回限流错误，正常请求也会被拒绝；如果遇到异常就全部放行，又失去了流量保护。

**分析：** Redis 调用失败和用户请求超限是两种情况，需要分开处理。异常分支里仍然要有限制，只是不能继续依赖已经不可用的 Redis。

**处理：** Redis 限流异常时，切换到进程内按用户计数的时间窗口，允许范围内的请求继续执行，超过阈值再拒绝。这层兜底只限制当前实例的请求量，多实例之间不共享计数，不能当成完整的分布式限流。

#### 8月29日：统计写入失败，不能跟着把跳转也弄失败

**问题：** 跳转前会收集访问数据并发送 Redis Stream 消息。这一步如果抛出异常，即使已经拿到了目标地址，也可能执行不到后面的重定向。

**分析：** 需要沿着“拿到地址 → 收集统计 → 发送消息 → 重定向”的顺序检查。问题不一定出在链接查询上，也可能是统计链路的异常没有被隔离。只处理消息发送异常还不够，收集 UV、UIP 时同样会访问 Redis。

**处理：** 在统计入口和消息发送位置分别增加异常处理，失败时记录日志，让跳转流程继续执行。目前优先保证跳转可用，丢弃的统计事件还没有持久化补偿，所以故障期间的统计会有缺口。

#### 8月30日：Redis 故障后，查库兜底也要限制并发

**问题：** 跳转流程不仅缓存查询依赖 Redis，布隆过滤器、空值缓存和分布式锁也依赖它。只给第一次读缓存加异常处理，后面仍然可能中断；直接让所有请求查数据库，又可能把压力转移过去。

**分析：** 需要把这些依赖点逐一检查，分别处理缓存读取、过滤器查询、锁获取和缓存回填失败。数据库兜底也要有边界，尤其是 Redis 故障时，不能默认数据库能承接全部流量。

**处理：** 为上述读取和锁获取异常接入数据库兜底，先查路由表取得分组标识，再查链接并核对启用状态、删除状态和有效期。兜底入口使用 100 个许可的信号量，最多等待 100 毫秒，拿不到许可就返回 503；缓存回填失败则记录日志，继续使用已经查到的目标地址。这个限制控制的是进入兜底的并发，不是数据库查询本身的超时。
